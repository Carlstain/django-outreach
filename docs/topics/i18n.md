# Internationalisation

- Message ids are English. Catalogues ship for French, Spanish, Portuguese and Brazilian
  Portuguese (`fr`, `es`, `pt`, `pt_BR`). They are drafts that a native speaker should review.
  See {doc}`languages` for what each language setting does.
- `USE_I18N` must be `True`, otherwise nothing is translated.
- The language is picked per view with `translation.override`, so the rest of your site is
  unaffected. The Outreach admin site and its login page use the staff member's choice or
  `OUTREACH_LANGUAGE`, the public unsubscribe pages use the `lang` of the link or
  `OUTREACH_LANGUAGE`, and each mail is rendered in its own language.
- No `LocaleMiddleware` is needed, and none is forced on the host project. The site renders its
  responses inside the override on purpose, since template rendering happens after a view returns.
- Variable labels use the message context `mail variable`, their examples `mail variable
  example`. Tag labels use `mail tag` and `mail tag example`.

## Translating your own tags

Rendering a mail runs inside the override of the mail's language, because tags such as `today` and
`greeting` are translated. A tag of your own can use `gettext` and `date_format` directly.

## Adding a language

Create `src/outreach/locale/<code>/LC_MESSAGES/django.po` by copying the French file and
translating it, add the code to `OutreachLanguage` and to the loops of `scripts/compile_messages.sh`
and `scripts/check_translations.sh`, then compile it:

```shell
pybabel compile -d src/outreach/locale -D django -l <code>
```

After editing a `.po`, run `scripts/compile_messages.sh`. The `.mo` files are generated and are
never edited by hand. All four catalogues are checked in CI.

Message ids that Django's own catalogues also translate (for example *Log out*) show Django's
wording, since Django's catalogues load first.
